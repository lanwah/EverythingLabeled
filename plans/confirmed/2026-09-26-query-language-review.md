## Q1 — `maxDepth` 触顶：截断还是 422？

**问题**：细则算法写深度静默截断，错误表/HTTP 曾写触及 `maxDepth` → 422，二者互斥。

**确认**：选推荐 **A**。

- 深度只截断：深子树不进集合，查询仍 `200`
- `422` 仅用于 `expandedTagLimit` 触顶，以及请求参数大于服务端上限
- 文档须去掉「触及 maxDepth → 422」的表述

---

## Q2 — 未知正词：整句清空还是按段作废？

**问题**：任一段任一正词解析失败时，是整句空结果，还是仅该段作废、其它 OR 段继续？

**确认**：选推荐 **A**（维持整句空）。

- 动机：宁可不返回，也不在用户以为 OR 扩召回时默默丢掉一段
- **补充**：程序日志须能明确记录并输出原因（token、段、规范化串等）

---

## Q3 — 别名以 `-` 开头时，正词怎么写？

**问题**：词法上以 `-` 开头一律负词，导致「别名以 `-` 开头」无法写成正词。

**确认**：选推荐 **A**。

- v1 **禁止**别名以 `-` 开头（创建/改别名校验失败）
- 查询语言不为此类别名开洞
- **补充**：日志须明确记录与输出

---

## Q4 — 保留词 `OR` 与别名 `or`？

**问题**：整 token 的 `OR`（大小写不敏感）永远是运算符，别名 `or` 无法用于 `q=`。

**确认**：选推荐 **A**。

- 禁止 `AliasNormalized ∈ { or, and, not }`（预留 `and`/`not`）

---

## Q5 — `maxDepth` / `expandedTagLimit` 合法区间？

**问题**：是否允许 `0`、下限、非法类型如何报错？

**确认**：选推荐 **A 变体**。

- `maxDepth ∈ [0, serverMax]`（`0` = 仅自身，合法）
- `expandedTagLimit ∈ [1, serverMax]`（`0` 非法）
- 非整数/负数等形状非法 → `400`；`> serverMax` → `422`
- **补充**：日志须明确记录与输出
- **后续补充（Q17）**：这些常量须在代码中集中定义并写好注释

---

## Q6 — 软失败（未知正词 → 200 空）对客户端是否可见？

**问题**：仅服务端日志，还是响应里也要能带说明？

**确认**：在推荐 A 基础上调整——

- 成功响应统一为至少三部分：**状态、信息、数据**（`status` / `message` / `data`）
- 返回 `200` 时，`message` 仍可带说明（未知正词等 notice）
- （后续 Q12–Q14 钉死信封细节，并推广到全 `/v1`）

---

## Q11 — 参数非法时的 HTTP 码切分？

**确认**：选推荐 **A**。

- 形状/范围下限非法 → `400 bad_request`
- `> serverMax` → `422 expansion_limit_exceeded`
- 日志区分 `param_invalid` vs `param_exceeds_server_max`

## Q12 — 成功信封字段名与 `status` 语义？

**确认**：选推荐 **A**。

- 成功路径 `status` 只有 `"ok"`
- 软失败仍 `"ok"`，靠非空 `message` 说明
- 硬错误走非 2xx + 错误信封

## Q13 — 新信封作用范围？

**确认**：选推荐 **A**。

- **全部** `/v1` 成功响应统一 `status` + `message` + `data`
- 业务体放进 `data`

## Q14 — 无说明时 `message`；错误信封是否对称？

**分析结论（用户追问）**：**利大于弊**，值得做成统一错误信封。

**确认**：

- 成功无说明：`message: null`；有说明：非空 string
- 错误改为：

```json
{
  "status": "error",
  "message": "...",
  "data": { "code": "...", "details"?: { } }
}
```

（原 `error` 对象信息迁入 `data`；`details` 由 Q18 确认保留为可选）

## Q19 — `status` 与 HTTP 状态码的不变量？

**确认**：选推荐 **A**。

- `status:"ok"` ⇔ 2xx
- `status:"error"` ⇔ 4xx/5xx
- 未知正词：HTTP 200 + `status:"ok"` + 非空 `message`（notice，不是 error）

---

## Q20 — 查询路径 notice / 日志 reason 成表？

**确认**：选推荐 **A**。

- 细则附录固定 reason 枚举
- **仅** `unknown_positive_term` 等点名项写入成功 `message`
- 深度截断、忽略负词：**只打日志**，不进成功 `message`

---

## Q21 — 查询并集分页的资源序？

**确认**：选推荐 **A**。

- `CreatedAt ASC, Id ASC`（query / preview / resources 无特殊排序时同一套）

---

## Q22 — 别名禁止规则收成「别名字符集」表？

**确认**：选推荐 **A+B**。

1. 不得以 `-` 开头  
2. 不得含 Unicode 空白  
3. 不得含 ASCII 控制字符  
4. `AliasNormalized ∉ { or, and, not }`  
5. 非空；其余字符 v1 允许（含 `:` 等）  
6. 违规 → `422 validation_failed`（`details` 带原因）+ 日志
